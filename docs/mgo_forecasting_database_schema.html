Current MVP: dashboard and purchase plans

Four tables. Each user owns at most one plan; each market series contains zero or more observations.

erDiagram
  USERS ||--o| PURCHASE_PLANS : owns
  MARKET_SERIES ||--o{ MARKET_OBSERVATIONS : contains
  USERS {
    uuid user_id PK "Generated UUID"
    text clerk_user_id UK "Clerk account ID - nullable during backfill"
    text email UK "Required"
  }
  PURCHASE_PLANS {
    uuid plan_id PK "Generated UUID"
    uuid user_id FK, UK "Required - internal user UUID"
    numeric quantity_mt "Required - greater than zero"
    date purchase_deadline "Required - single deadline"
    date scenario_as_of_date "Required - historical scenario"
  }
  MARKET_SERIES {
    uuid series_id PK "Generated UUID"
    text series_key UK "Required"
    text source_name "Required"
    text source_url "Nullable"
    text currency_code "Nullable"
    text unit "Nullable"
    text price_definition "Nullable"
    text contract_description "Nullable"
  }
  MARKET_OBSERVATIONS {
    uuid observation_id PK "Generated UUID"
    uuid series_id FK "Required"
    date observation_date "Required - unique with series_id"
    numeric value "Required"
    text value_type "Required"
    timestamptz availability_timestamp "Nullable"
  }

PK = primary key; FK = foreign key; UK = unique constraint. Observations have a composite unique constraint on (series_id, observation_date).

How this matches the MVP

  • The updated purchase-plan screens use quantity in MT, one purchase deadline, and a read-only historical scenario date. Time remaining is calculated from the dates.
  • There is no separate profile table. Display names can come from Clerk. Passwords are not stored here.
  • User UUIDs are generated with gen_random_uuid(). The unique Clerk ID is nullable while existing accounts are mapped; new Clerk-backed users need their verified Clerk ID.
  • The fresh schema has no Supabase Auth foreign key, signup trigger, or auth-based policies. Supabase can still host PostgreSQL.
  • RLS is enabled on all four tables with no client-facing policies. Direct access by ordinary client roles is denied. Trusted backend access needs suitable server-only database privileges and explicit user ownership checks.
  • Deleting a user cascades to their plan. Deleting a plan leaves the user and market data intact. Deleting a market series is restricted while observations reference it.
  • Unverified market unit and contract metadata stays nullable. Monetary series use USD by convention; non-monetary indicators may have no currency.
