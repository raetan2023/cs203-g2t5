Local fixes only — not deployed to Supabase. These four fields were already required by the logical design, but the original SQL allowed NULL. The corrected SQL now enforces them. Compare the actual Supabase schema and migration history before applying the candidate migration.

Only these four constraints changed in the SQL. Types, relationships, one-plan uniqueness, positive quantity checks, and deletion behaviour are unchanged. NOT NULL rejects missing values; it does not validate blank text, allowed value-type labels, deadline ordering, or urgency rules.

Migration checks also verified rejection of existing NULL data, rollback without partial changes, and repeat execution. Tests used disposable PostgreSQL with placeholder Supabase auth objects; Clerk, RLS/user isolation, APIs, and persistence across sessions/restarts were not tested.

Before changing shared Supabase

  1. Get the actual schema and applied migration history from Wunna. Confirm the target tables, column types, constraints, triggers, policies, and database roles; local files do not prove what is deployed.
  2. Check existing rows for NULL in all four fields. Agree corrections using verified values with the relevant owner. The candidate migration aborts if any remain; it does not invent defaults or delete records.
  3. Agree the migration runner and deployment timing with Wunna, confirm a recovery point, and test on a disposable copy of the target. The migration uses exclusive table locks with timeouts.
  4. Apply the reviewed migration through the agreed process, then verify the four constraints and backend integration. Do not use the full fresh-schema script as an upgrade: CREATE TABLE IF NOT EXISTS does not update existing columns.

Constraints and saved-result behaviour

AreaSchema rule
Plan ownershipOne plan per user: user_id is required and unique. Quantity must be positive. Derive urgency from the scenario date and purchase deadline; thresholds and calendar remain TBC. Enforce ownership for all private reads and writes.
Observation uniquenessComposite unique key (series_id, observation_date). Different price measures/contracts use distinct series keys. Unknown publication time remains null; it is not inferred from observation date.
Currency and unitsMonetary series and forecasts use USD. Non-monetary indicators may have no currency. Gasoil physical unit, price definition, and contract definition remain TBC. Unit-dependent calculations require verified metadata.
ForecastsStore origin and target dates, ordered bounds, currency/unit, forecast method, validation status, and uncertainty method. Exact horizon remains TBC. Method/status replace the ambiguous is_proxy_estimate flag.
Plan editsUpdate the current plan in place. Existing PURCHASE_ANALYSES keep immutable input snapshots; new calculations use the updated plan. Referenced forecasts and observations must not change in place.
Plan deletionPlan → analyses → impacts and recommendations → decisions are cascade-deleted. Shared users, market data, forecasts, and model versions remain. Protect referenced shared records from deletion.
Recommendations and decisionsRecommendations reference an analysis, which identifies the forecast and model. Save new recommendations under new IDs. At most one response per recommendation; the responding user must own the plan. Ignore/change-response semantics remain TBC.

Proposed percentage-transfer mapping

M_h = M_0 × (G_h / G_0): apply predicted Gasoil percentage movement to a dated MGO anchor. This remains an experimental baseline, not a validated relationship.

If selected, require the source Gasoil forecast, Gasoil origin observation, and MGO anchor references. Origins/targets must align, the Gasoil denominator must be positive, and units/contracts must be comparable. These references are optional for methods that do not use this mapping. An old anchor requires a separately agreed policy; mapped bounds alone do not establish calibrated MGO uncertainty.

Purchase impacts use snapshotted quantity Q and reference P0 with MGO bounds [L,U] in USD/MT: reference Q×P0; forecast [Q×L,Q×U]; difference [Q×(L-P0),Q×(U-P0)].
